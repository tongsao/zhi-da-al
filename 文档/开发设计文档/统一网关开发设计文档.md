# 统一网关开发设计文档

> 版本：v1.0 ｜ 日期：2026-10-21
> 配套文档：《统一网关需求文档.md》
> 设计原则：**与现有业务逻辑物理隔离**，新增代码集中在 `gateway/`、`llm_gateway/` 两个独立目录；对现有文件的改动收敛到最小集合（`main.py` 一行 import + 一行启动调用、模型初始化收敛两个文件、前端改造）。

## 1. 总体架构

### 1.1 架构形态

FastAPI 应用内集成，不新增部署单元。三个横切点以「中间件」方式挂载：

```
请求 → [Auth 中间件] → [RateLimit 中间件] → [Audit 中间件] → 业务路由(现有 controller 不变)
       └──────── 身份识别+准入 ────┘  └─ 按维度限流 ─┘  └── 全程审计收尾 ─┘
                                              │
                              [llm_gateway 统一模型入口] ← 业务侧模型调用收敛
                                     └─ 重试/降级/每日token预算/用量上报
```

- **认证 + 限流 + 审计**：三个独立中间件横切所有 `/api/v1/*` 请求，业务 controller 零改动。
- **RBAC 依赖**：`gateway/deps.py` 提供 `get_current_user` / `require_admin`，注入到管理员专属接口与网关管理接口。
- **模型网关**：`llm_gateway/` 独立包。**P0 评审修正**：不做「函数式统一入口」（现有业务均持模型实例自行 invoke，无法收口），改为**模型计数代理包装**——`getModel()/getEasyMode()` 返回与原模型同接口的包装实例，自动完成限额预检与用量上报；重试/降级用 LangChain 原生 `with_retry/with_fallbacks` 装配（见 §9.2）。业务逻辑完全不变。

### 1.2 中间件注册顺序（Starlette 洋葱模型）

```
app.add_middleware(AuditMiddleware)      # 先 add → 最内层（request 最后执行、response 最先收尾 → 记录耗时）
app.add_middleware(RateLimitMiddleware)
app.add_middleware(AuthMiddleware)       # 后 add → 最外层（request 最先执行 → 先认证后限流）
```

执行序：**Auth(识别身份、准入) → RateLimit(按身份限流) → Audit(包全程、落库结果)**。
三中间件通过 `request.state` 传递上下文（身份、审计结果），互不直接依赖。

## 4. 安全设计

### 4.1 密码哈希（零第三方依赖）

stdlib `hashlib.pbkdf2_hmac('sha256', password, salt, iterations)`：

```
存储格式: pbkdf2_sha256$100000$<salt_b64>$<hash_b64>
salt: secrets.token_bytes(16) 随机
```

- 校验时按格式串解析参数重算比对（`hmac.compare_digest`）。
- 迭代次数、锁定阈值、锁定分钟数均走 `.env` 配置。
- 不引入 passlib/bcrypt（版本兼容坑多），避免新增依赖风险。

### 4.2 JWT（PyJWT，HMAC-SHA256）

- 签名密钥 `JWT_SECRET` 配置于 `.env`；有效期 `JWT_EXPIRE_HOURS=12`，无 refresh（需求 §5.1）。
- **载荷**：

```json
{
  "sub": "1",              // user id
  "role": "admin",          // admin / user
  "username": "admin",
  "must_change_password": true,
  "pwd_changed_at": 1729500000,   // 签发时对密码变更时间的快照
  "iat": 1729500000,
  "exp": 1729543200
}
```

- **无状态 + 状态兜底**：JWT 本身无状态，但需求要求「停用/改密后即时失效」，故认证中间件在每次请求校验 token 后，**按主键查一次 zd_user**，核对三项：
  1. `is_active=1`（停用 → 401）
  2. `pwd_changed_at` ≤ 载荷快照（改密 → 401，旧 token 作废）
  3. `must_change_password` 与载荷一致
  查库走主键索引，量级可接受。

### 4.3 API Key

- 生成：`zd_` + `secrets.token_urlsafe(32)`；**明文仅创建响应返回一次**。
- 存储：仅存 `sha256(明文)` hex（`key_hash` 唯一索引）。
- 传递：请求头 `X-Api-Key: <明文>`（机器调用统一，与 JWT 的 `Authorization: Bearer` 区分）。
- 校验：哈希比对命中 → 核对 `is_active`、`expires_at`、来源 IP ∈ `ip_whitelist`；任一不满足统一返回「未授权」（需求 §7.1，不暴露具体原因）。
- 轮换：生成新 key 记录、删除旧记录 → 旧 key 立即失效。

### 4.4 凭证识别规则

1. 携带 `X-Api-Key` → 按密钥识别（仅「密钥准入」分组可用，见 §8）
2. 携带 `Authorization: Bearer <jwt>` → 按用户识别
3. 两者皆无 → 非豁免路径直接 401（caller_type=anonymous）

### 4.5 统一错误码（HTTP 状态码 + 响应体 code）

| HTTP | code | 场景 | 前端处理 |
|---|---|---|---|
| 200 | 0 | 成功 | |

> 注：`code` 为**字符串**（沿用现有 `schema.schemas.Response.code: str`），前端比较时统一 `String(code) === '0'`。
| 401 | 4010 | 未登录/凭证无效/过期/密钥无效 | 跳登录 |
| 403 | 4030 | 角色权限不足 | 提示无权限 |
| 403 | 4031 | 需先修改密码（凭证有效但功能受限） | 跳强制改密页 |
| 423 | 4230 | 账号已锁定（输错 5 次锁 30 分钟） | 提示稍后再试 |
| 429 | 4290 | 请求过于频繁 | 提示稍后重试 |
| 429 | 4291 | 当日模型用量已用尽 | 提示次日恢复 |

响应体统一沿用 `{code, message, data}`（`schema.schemas.Response`）。

## 5. 中间件设计

### 5.1 Auth 中间件（`gateway/middleware.py`）

```
Auth(request):
  1. 豁免判定：路径 ∈ {GET /, GET /api/v1/health, POST /api/v1/auth/login} → 放行
  2. 强制改密例外：POST /api/v1/auth/change-password 且用户处于 must_change → 放行（仅此接口）
  3. 解析凭证（见 §4.4）→ 识别 caller_type / caller_id
  4. 准入分组判定（见 §8 分组表）：
     - 密钥分组：仅接受 X-Api-Key；带 JWT 或无凭证 → 403
     - 管理员分组：需 role=admin → 否则 403
     - 通用分组：用户/密钥任一有效即可
  5. must_change_password=1 且访问非改密接口 → 403/4031
  6. request.state.caller = {type, id, role}    # 供限流/审计/业务依赖使用
```

### 5.2 RateLimit 中间件

```
RateLimit(request):
  1. 取 request.state.caller → 限流键集合：IP 键恒有；有身份时追加 user:{id} / key:{id}
  2. 按路径匹配接口分组（§7 分组表）→ 取得该分组的配额表（多维度）
  3. 分组配额为「不限」（health / auth_login）→ 直接放行，不做任何计数
  4. 逐个维度 consume()：任一超限 → 429/4290，短路返回
  5. 放行
```

### 5.3 Audit 中间件

```
Audit(request):
  request.state.audit_start = now()
  try:
      response = call_next(request)            # 认证/限流在更外层，已决定成败
  except Exception:
      status = error；code = 500
  finally:
      1. 豁免：路径为 /api/v1/health → 不落库（防刷表）
      2. 认证类（POST /api/v1/auth/login、/api/v1/auth/change-password）必记，登录失败也记
      3. 其余请求按 request.state.caller + 响应结果组装一条审计
      4. await run_in_threadpool(audit_write, row)   # 同步 SQLAlchemy 提交，避免阻塞事件循环
```

> 认证类接口本身是豁免路径，但审计**必须记录**——所以「豁免」与「必审」是两个独立维度：`豁免路径`（不校验凭证）∩ `豁免审计`（health 等内部探测）。
>
> **SSE 流式接口（POST /chat）时长说明（评审 P1）**：`call_next` 对流式响应在**响应对象创建后即返回**，`duration_ms` 只覆盖到「响应创建时刻」，不等于用户完整接收时长。本期在审计层不做逐帧埋点（改动侵入业务），SSE 的精确耗时列为已知边界（§14 风险表），如需精确值后续在 chatService 内补一次计时。
>
> **审计写失败不阻塞业务（评审 P2）**：`audit_write` 落库失败仅 `logger.error`，不向请求方抛错、不重试——网关定位是「尽量记」，业务可用性优先；失败率可另挂监控看板（本期不做）。

## 6. 限流器设计（`gateway/ratelimit.py`）

内存令牌桶 + `threading.Lock`：

```python
class Bucket:
    capacity: float          # 突发容量 = 配额
    refill_rate: float       # 每秒补充 = 配额/60
    tokens: float

class BucketStore:
    # key: (group, dimension, dimension_key) -> Bucket
    def consume(group, dim, key, amount=1) -> bool: ...
    def prune():  # 惰性 + 定时清理超过空置期的桶
```

- **维度键**：IP → `ip:<addr>`；用户 → `user:<id>`；密钥 → `key:<id>`。
- **重启清零**：内存实现，属已确认可接受边界（需求 §5.6.4）。
- 清理策略（评审 P2）：每次操作顺带删除 `last_access` 超过其**所属分组配额周期 × 2** 的桶——各分组周期以自身配额定义为准（`qa` 1min、`eval_trigger` 1min、`default` 1min 等，统一不拍一个固定阈值，因周期可能随配额调整）；无独立定时器（避免线程管理复杂度）。
- 未来替换 Redis：`BucketStore` 抽象为接口，实现类可换，单机期仅内存实现。

## 7. 接口分组与权限/限流映射

网关层用「路径匹配规则」实现分组，业务 controller 零改动。匹配规则从上到下取首个命中。

| 分组 | 路径规则 | 准入 | 限流 | 说明 |
|---|---|---|---|---|
| `health` | `GET /api/v1/health` | 豁免 | 不限 | 不审计 |
| `auth_login` | `POST /api/v1/auth/login` | 豁免 | 不限 | 必审计 |
| `auth_ops` | `POST /api/v1/auth/change-password`、`GET /api/v1/auth/me` | 用户 | 通用 | 改密在 must_change 下放行 |
| `key_only` | `POST /api/v1/ai-check/projects`、`POST /api/v1/ai-check/files` | **仅密钥** | 通用 | 信披中心推送 |
| `qa` | 前缀 `/api/v1/qa/*`（POST /chat、POST /chat/stop、GET /chat/conversation_id、GET /chat/gethistory、DELETE /chat/conversation_id、POST /feedback、GET /feedback/stats、GET /feedback/list） | 用户 | IP 10/min、user 30/min、key 30/min | 问答含流式与历史 |
| `upload` | `POST /api/v1/documents` | 用户 | user 5/min、key 5/min | 文件上传 |
| `eval_trigger` | `POST /api/v1/eval/run`、`POST /api/v1/eval/gen/run`、`POST /api/v1/eval/gen/runs/*/rerun` | **仅 admin** | admin 1/min | 高成本触发 |
| `doc_delete` | `DELETE /api/v1/documents/{id}` | **仅 admin** | 通用 | |
| `rule_toggle` | `PUT /api/v1/ai-check/rules/{id}/enabled` | **仅 admin** | 通用 | 规则开关 |
| `admin_mgmt` | `/api/v1/users*`、`/api/v1/api-keys*`、`/api/v1/audit*`、`/api/v1/usage*` | **仅 admin** | 通用 | 网关管理路由 |
| `default` | 其余 `/api/v1/*` | 用户 | user/key/IP 各 60/min | 兜底 |

> 现有业务接口归属核对（与 §3.2 权限矩阵一致）：
> - 业务员可用：问答全部、文档上传/列表/下载、kb/stats、ai-check 查看类（projects GET / files 不可 / results / rules）、评测查看类、feedback 全部。

> - 密钥独有：ai-check 推送类（projects POST / files POST）。

## 8. 网关新增 API

### 8.1 认证

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/auth/login` | 豁免 | body: {username, password} → {token, user{id,username,role,display_name,must_change_password}}；输错计数、锁 30 分钟；锁定返回 4230 |

### 8.2 用户管理（admin）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/users` | 分页列表（page/page_size/username 模糊） |

### 9.2 模型计数代理（`gate.py`）——P0 评审后修订

> **评审发现**：现有业务拿模型实例后自行调用（`agent.stream`、`chain.invoke`、`model.bind`，见 [agent_tools.py](file:///e:/PythonProject/PythonProject/ZhiDaAl/tools/agent_tools.py#L177-L181)、evalService/chatService 等 10+ 处），不存在可统一的「函数入口」。若按原设计做 `gate.chat()` 函数入口，SSE 流式、后台评测线程的限额/用量将全部失效。**故改为「计数代理包装」**：`getModel()/getEasyMode()` 返回与原模型同接口的包装实例，业务代码**零改动**。

```python
class CountingChatModel:                    # 实现与原 ChatModel Runnable 相同接口
    def __init__(self, inner, role):
        self.inner = inner                  # 已装配 timeout + with_retry + fallbacks 的原模型
        self.role = role                    # chat / rewrite

    def bind(self, **kw): return CountingChatModel(self.inner.bind(**kw), self.role)
    def __or__(self, other): return self.inner.__or__(other)          # 支持 chain = prompt | model
    # invoke / ainvoke / stream / astream / batch / abatch 统一走 _call
    def _call(self, method, *a, **kw):
        if not in_batch_exempt():            # 批量豁免时跳过预检（见 9.3）
            usage.precheck(self.role)        # 超限 → 抛 QuotaExceeded（4291）
        resp = getattr(self.inner, method)(*a, **kw)   # 委托原模型
        usage.record(self.role, extract_usage(resp))   # 无论成败都记
        return resp
```

- **重试/降级**：不在包装器内自实现，用 LangChain 原生能力装配在 `inner` 上——`model.with_retry(max_retries=2, retry_if_exception_type=(TimeoutError, OSError))`（指数退避由 LangChain 内部处理，仅重试瞬时错误，4xx 业务错误不重试）；`model.with_fallbacks([backup])` 在 `GATEWAY_MODEL_FALLBACK=true` 时启用。stream 与 async 全兼容，agent 内部节点调用同样被覆盖。
- **embedding 同理**：`CountingEmbeddingModel` 包装 embedding，拦截 `embed_query/embed_documents`，token 计入 input。
- **批量豁免**：评测后台线程进入前设置线程局部标记 `batch=True`（threading.local，见 9.3），线程内各次 invoke 跳过 precheck、仍逐次 record；任务启动时单独执行一次预检。
- **错误形态**：模型层异常统一抛 `ModelGatewayError`（不吞业务错误），业务层提示「模型服务暂不可用」；chat 与 embedding 各自独立包装与实例，互不影响。

### 9.3 用量与限额（`usage.py`）

- 进程内 `{date: {kind: tokens}}` 计数 + `threading.Lock`；日期切换自动重置为新日。
- 每日首次有调用时，把 `stat_date=昨天` 的累计值写入 `zd_model_usage`（线程池提交）。
- `DAILY_TOKEN_LIMIT` 为全模型共用总限额：`precheck` 校验 `当日累计 + 本次估算 ≤ 限额`。
- **批量豁免（threading.local，评审 P1-3）**：评测后台线程（`threading.Thread`，见 evalService 生成评测）入口处 `set_batch(True)` 置线程局部标记，`finally` 中清除；`gate._call` 先查该标记，置位则**跳过逐次 precheck、仍逐次 record**；主线程不受影响。任务启动时单独执行一次预检（按估算总量），中途超限不中断（保证进行中评测放行，需求 §5.9.3），结束后按实际用量落库（超限部分也如实记录）。
- 用量提取：openai 兼容响应 `usage.prompt_tokens / usage.completion_tokens`；embedding 走 `usage.prompt_tokens` 计为 input。

### 9.4 业务侧收敛点（例外改造，仅 2 处）

- `agent/initChatModel.py`：`getModel()` → `llm_gateway.providers.get_chat()`（返回 **CountingChatModel 包装实例**，接口与原 model 一致，含 `bind/__or__/invoke/ainvoke/stream/astream/batch` 及 `model_name` 等属性代理，业务侧调用处零改动）；`getEasyMode()` → `get_rewrite()`（同上包装）；`getCheckpointer()/getRiskGuard()` 不动。
- `agent/rag/initEmBedding.py`：embedding 实例获取改经 `llm_gateway.providers.get_embedding()`（**CountingEmbeddingModel**，拦截 `embed_query/embed_documents`）。

> 收敛验证点：`ragFileService.py` 读 `getModel().model_name`、`evalService.py` 模块级 `judge_chain = JUDGE_PROMPT | getModel().bind(...)`、`tools/agent_tools.py` 的 `getChatAgent()` 等 10+ 调用处**均不改动**——包装器保证类型与行为兼容（评审 P0 结论）。

收敛后 Langfuse 埋点保留（工厂统一挂 `CallbackHandler`），评测/问答 trace 不受影响。

### 12.2 登录态存储与守卫

- `stores/auth.js`（Pinia）：`token / user`，`localStorage` 持久化（刷新不丢）；actions：`login / logout / changePassword / fetchMe`。
- 路由守卫（`router/index.js` `beforeEach`）：
  - `requiresAuth` 且无 token → `/login`
  - 已登录且 `must_change_password` 且目标非 `/force-change-password` → 强制改密页
  - 已登录且目标为 `/force-change-password` 但非 must_change → `/qa`
  - `meta.roles` 不含当前角色 → `/qa`（提示无权限）
- **根路径处理**：现有 `/` redirect `/qa`（`requiresAuth`）→ 未登录时守卫拦截跳 `/login`；已登录直接进 `/qa`，无需单独定义 `/login` 为公开路由。
- **评测页粒度：页面级 vs 按钮级（评审 P2）**：`/qa` 下评测**查看类页面**（评测列表/详情/结果页）对 `admin` 与 `user` **都可见**（后端查看类接口为通用准入）；「触发评测 / 重跑」**按钮**仅 `role === 'admin'` 时渲染（按钮级显隐，不与页面级权限耦合）。前端按钮隐藏属体验优化，**安全边界仍由后端 `eval_trigger` 分组强制**（仅 admin 可调，见 §7），不因前端隐藏而放宽。
- 现有业务路由补 `meta: { requiresAuth: true }`；管理路由补 `meta.roles: ['admin']`；`/login`、`/force-change-password` 为公开/半公开（后者需登录但无角色限制）。

### 12.3 API 层

- `api/index.js` **增强现有 axios 拦截器**（非新增）：请求拦截器加 `config.headers.Authorization = Bearer <token>`（从 auth store 读取）；
- 响应错误分支 **沿用现有 `err` 分支**，新增演进：HTTP 401 → 清 token 跳 `/login`（需在现有 blob 还原后再判断 status）；403/4031（带 `body.code`）→ 4031 跳强制改密页、4030 提示无权限；429/423 → ElMessage 提示；现有 `blob` 错误还原逻辑保留；
- `chatStream`（SSE 走 fetch）：补 `headers: { Authorization: Bearer <token> }`（关键，中间件层校验），并处理非 200 响应——若返回 401 应跳登录（SSE 的 HTTP 状态是快速失败通道）；
- 新增 `api/gateway.js`：login/changePassword/me、users、api-keys、audit、usage 的调用封装。

> 注意：当前 `api/index.js` 拦截器是全局单例，401 跳登录需**去掉死循环保护**（跳转只在收到 401 时触发一次，guard 里已登录校验会自然兜底）。

### 12.4 布局

- `App.vue`：侧边栏新增「系统管理」分组（用户管理/密钥管理/审计/用量），按角色过滤；顶栏右侧加用户下拉（显示名、修改密码、退出登录）；`navItems` 结构不变、增加 `roles` 字段。
- 登录态过期统一由拦截器跳登录，页面内无需各自处理。

## 14. 风险与边界

| 项 | 说明 |
|---|---|
| 内存限流重启清零 | 已确认可接受；BucketStore 接口化，未来可换 Redis |
| 中间件查库每请求一次 | 主键查询量级可控；并发上升后可加内存缓存 + 短 TTL |
| SSE 鉴权 | 认证在中间件完成，前端 fetch 必须带 header（已列入 12.3） |
| SSE 审计时长失真（评审 P1-1） | BaseHTTPMiddleware 对流式 `call_next` 在响应创建时即返回，`duration_ms` 未覆盖完整流时长；已确认本期不逐帧埋点，精确耗时列为已知边界（§5.3 注） |
| 禁用文档（评审 P1-2） | `/docs` `/redoc` `/openapi.json` 关闭 → 开发期调试便利性下降，联调靠 Postman/自建最小样例；对外的接口面收敛为「零自助文档」 |
| 评测线程 | 批量任务走 `batch()` 语义，启动预检 + 结束上报，中途放行；评测线程数过多会放大 token 消耗，超限部分如实落库供对账 |
| 用量估算偏差 | 单次调用按响应 usage 精确计数；批量任务估算值用于预检，实际值以结束上报为准 |
| admin 全锁自救（评审 P1-4） | 禁止停用最后一个启用 admin（§8.2 保护规则）+ 登录锁定仅锁登录尝试（锁定 30 分钟自动解）；兜底：直接改库 `UPDATE zd_user SET locked_until=NULL` 或 DB 层重置密码；文档备注到运维手册（本期不提供「绕过锁定」API，避免留后门） |
| MySQL JSON 兼容（评审 P1-5） | `zd_api_key.ip_whitelist` 用 MySQL `JSON` 类型；ORM 直接用 `JSON`，避免 SQLAlchemy `JSONB`（Postgres 专属）导致的方言不兼容；序列化/反序列化由驱动处理，值比较用 `JSON_EXTRACT` 不在应用层拼字符串 |
| 审计写失败（评审 P2） | 落库失败仅记日志不阻塞业务（§5.3 注） |
| 代理 IP | 单机直连取 `Request.client.host`；若未来加代理需引入可信头解析（本期不做） |
| admin 弱口令 | 预置 123456 但强制改密兜底，改密前业务不可用（需求 §5.2） |
