# 统一网关测试案例文档

> 版本：v1.0 ｜ 日期：2026-10-21
> 配套文档：《统一网关需求文档.md》《统一网关开发设计文档.md》
> 说明：本测试案例以两份配套文档约定的行为为准编写，用例中的路径、错误码、配额均与设计文档 §7/§8 及当前实现核对一致。网关中间件挂载与 `initGateway()` 接入 `main.py` 后即可按本案例执行。

---

## 1. 概述

### 1.1 目的

验证「统一网关」P0 范围各项能力满足需求文档验收标准：

- 建立统一的调用方准入体系（登录凭证 / API 密钥双轨）；
- 按调用方维度实施限流，阻断异常调用与成本失控；
- 调用审计落库与事后追溯；
- 模型调用收敛、超时重试、主备降级与每日用量护栏；
- 横切接入，不与现有业务逻辑耦合，AI 质检等现有功能不回归。

### 1.2 范围

覆盖需求文档 P0 全部功能点：登录与登录态、预置账号与强制改密、用户管理、API 密钥管理、接口身份识别与准入、访问限流、调用审计、统一模型接入、模型用量与每日限额、前端页面与拦截、初始化与配置、回归验证。

### 1.3 测试入口约定

- 服务地址：`http://127.0.0.1:8000`（单机本地联调默认端口）；
- 登录凭证请求头：`Authorization: Bearer <token>`；
- 机器调用方凭证请求头：`X-Api-Key: <明文密钥>`；
- 统一响应体：`{code, message, data}`，`code` 为**字符串**，断言比较统一 `String(code) === '0'`；
- 统一错误码（设计文档 §4.5）：

| HTTP | code | 场景 |
|---|---|---|
| 401 | 4010 | 未登录 / 凭证无效 / 过期 / 密钥无效 |
| 403 | 4030 | 角色权限不足 |
| 403 | 4031 | 需先修改密码（凭证有效但功能受限） |
| 423 | 4230 | 账号已锁定（输错 5 次锁 30 分钟） |
| 429 | 4290 | 请求过于频繁 |
| 429 | 4291 | 当日模型用量已用尽 |

### 1.4 用例编号规则与优先级

- 编号：`TC-<模块字母>-<序号>`，模块映射：A=登录、B=强制改密、C=用户管理、D=密钥管理、E=准入、F=限流、G=审计、H=模型网关与用量、I=前端、J=初始化配置与安全、K=回归。
- 优先级：P0=验收核心（必须全部通过方可发布）；P1=重要（正常发布应通过）；P2=次要/边界/优化项。

## 2. 测试环境与准备

### 2.1 环境要求

- Python 3.x + 本仓库依赖（`pyproject.toml` 已安装），MySQL 可用，Langfuse 可降级不阻塞；
- `.env` 存在且配置 `JWT_SECRET`（≥32 字符）；其余网关配置项可先保持默认；
- 服务启动：`python main.py`（或 PyCharm 调试启动），启动日志无网关相关异常；
- 前端：`frontend/` 执行 `npm install` 后 `npm run dev` 启动。

### 2.2 推荐测试配置（`.env` 增补）

```ini
JWT_SECRET=<随机长串，>=32字符>
JWT_EXPIRE_HOURS=12
PASSWORD_ITERATIONS=100000
LOGIN_LOCK_THRESHOLD=5
LOGIN_LOCK_MINUTES=30
AUDIT_RETENTION_DAYS=90
RL_QA_IP_PER_MIN=10
RL_QA_USER_PER_MIN=30
RL_QA_KEY_PER_MIN=30
RL_EVAL_TRIGGER_PER_MIN=1
RL_UPLOAD_PER_MIN=5
RL_DEFAULT_PER_MIN=60
DAILY_TOKEN_LIMIT=<按用例需要设置，可 0=不限>
GATEWAY_MODEL_FALLBACK=false
```

> 限流/锁定/限额相关用例建议在**独立环境**或临时调整配置后执行，避免与其他用例互相干扰；执行完恢复默认值。

### 2.3 测试数据准备

| 数据 | 准备方式 | 说明 |
|---|---|---|
| admin 账号 | 系统初始化自动创建 | `admin / 123456`，role=admin，must_change_password=1 |
| 业务员账号 | 管理员登录后经 `POST /api/v1/users` 创建 | 建议 `sales01 / 123456`，role=user |
| 信披密钥 | 管理员经 `POST /api/v1/api-keys` 创建 | 绑定 IP `127.0.0.1`，明文仅创建时返回，测试期间保存使用 |
| 被拒绝类请求数据 | 用例执行过程产生 | 用于审计断言 |

### 2.4 执行顺序建议

1. 模块 J（初始化与配置）→ 确认服务可安全启动；
2. 模块 A/B（登录与强制改密）→ 打通 admin 主流程；
3. 模块 C/D（用户、密钥）→ 准备业务员与密钥数据；
4. 模块 E/F/G（准入、限流、审计）→ 网关横切能力；
5. 模块 H（模型网关与用量）→ 建议独立环境配置限额执行；
6. 模块 I（前端）→ 页面联调；
7. 模块 K（回归）→ 全链路回归确认无影响。

## 3. 用例公共约定

- 下文「携带 admin token」「携带 user token」均指先用 `POST /api/v1/auth/login` 登录取得的 `data.token`；登录接口本身是豁免路径，无 token 即可调用。
- 「强制改密未完成」状态通过预置 admin（must_change_password=1）或管理员重置业务员密码制造。
- 审计断言依赖审计线程池异步落库，断言前建议等待 1~2 秒或查询重试。
- 限流断言与用例执行**并发次数**强相关，步骤中标注的次数为「同维度连续发起」计数。

## 4. 测试用例

### 4.1 模块 A：登录与登录态

#### TC-A-01 预置 admin 首次登录成功（进入强制改密状态）
- 优先级：P0
- 前置：系统初始化完成，admin 账号存在。
- 步骤：
  1. `POST /api/v1/auth/login`，body `{"username": "admin", "password": "123456"}`。
- 预期：
  1. HTTP 200，`code="0"`；`data` 含 `token` 与 `user{id, username="admin", role="admin", display_name, must_change_password=true}`；
  2. `zd_call_audit` 新增一条 `POST /api/v1/auth/login` 的 `success` 记录（caller_type=user，caller_id=admin 的 id）。
- 备注：须先完成 TC-B 改密，否则后续用例无法以正常状态使用 admin。

#### TC-A-02 业务员正确密码登录成功
- 优先级：P0
- 前置：已存在业务员账号（未强制改密或已改密）。
- 步骤：
  1. 以业务员用户名 + 正确密码调用登录接口。
- 预期：
  1. HTTP 200，`code="0"`；`data.user.role="user"`，`must_change_password` 与账号当前状态一致；
  2. 登录成功记录写入审计。

#### TC-A-03 密码错误返回统一提示
- 优先级：P0
- 步骤：
  1. 使用正确用户名 + 错误密码调用登录接口。
- 预期：
  1. 返回统一文案「用户名或密码错误」，HTTP 401 / `code="4010"`；
  2. **不得**出现「密码错误」「账号不存在」等区分性文案（防账号枚举）；
  3. 登录失败记录写入审计（status=unauthorized）。
- 备注：该失败会累计 `failed_attempts`，连续执行会触发锁定，测试时注意计数。

#### TC-A-04 账号不存在返回统一提示
- 优先级：P0
- 步骤：
  1. 使用不存在的用户名 + 任意密码调用登录接口。
- 预期：
  1. 与 TC-A-03 返回完全一致的文案与码（401/4010），不暴露账号是否存在。

#### TC-A-05 停用账号登录被拒（统一提示）
- 优先级：P0
- 前置：管理员已将某业务员账号停用。
- 步骤：
  1. 使用停用账号的正确密码调用登录接口。
- 预期：
  1. 返回「用户名或密码错误」（401/4010），不区分停用原因；
  2. 登录失败记录写入审计。

#### TC-A-06 连续输错 5 次触发账号锁定
- 优先级：P0
- 前置：使用业务员账号，确认其未被锁定。
- 步骤：
  1. 连续 5 次以错误密码调用登录接口；
  2. 第 6 次以**正确密码**调用登录接口。
- 预期：
  1. 第 1~5 次均返回 401/4010「用户名或密码错误」；
  2. 第 6 次返回 HTTP 423 / `code="4230"`（账号已锁定，提示稍后再试），即使密码正确也不放行；
  3. `zd_user.failed_attempts=5`，`locked_until` 为当前时间 +30 分钟。
- 备注：锁定仅影响新的登录尝试（需求 §5.1 Assumption）。

#### TC-A-07 锁定期满后自动解锁可登录
- 优先级：P1
- 前置：账号处于锁定状态。
- 步骤：
  1. 等待 30 分钟（或测试环境临时调小 `LOGIN_LOCK_MINUTES`、或 DB 将 `locked_until` 置 NULL 加速）；
  2. 使用正确密码调用登录接口。
- 预期：
  1. 登录成功，`failed_attempts` 归零。

#### TC-A-08 登录态 12 小时有效、过期后拒绝
- 优先级：P0
- 前置：获取一个有效 token。
- 步骤：
  1. 携带 token 调用任一业务接口（如 `GET /api/v1/qa/chat/conversation_id`），验证正常；
  2. 构造/获取一个已过期 token（临时调小 `JWT_EXPIRE_HOURS` 后签发，或用伪造 exp 的 token），携带调用同一接口。
- 预期：
  1. 有效 token 正常通过；
  2. 过期 token 返回 HTTP 401 / `code="4010"`，前端据此跳登录。
- 备注：本期无 refresh 机制，过期即需重新登录；临时调小 `JWT_EXPIRE_HOURS` 需重启服务生效，测试后务必改回。

#### TC-A-09 锁定不影响已登录会话继续使用
- 优先级：P1
- 前置：业务员已登录持有 token；后因输错触发锁定。
- 步骤：
  1. 使该业务员账号被锁定；
  2. 携带锁定前签发的 token 调用业务接口。
- 预期：
  1. 请求仍正常通过（锁定仅拦截新的登录尝试）。
- 备注：对应需求 §5.1 Assumption 项，属 TBD 待业务确认项，先按此验证。

### 4.2 模块 B：预置账号与强制改密

#### TC-B-01 首次登录返回强制改密标记
- 优先级：P0
- 步骤：
  1. 用初始/重置密码登录一个 must_change_password=1 的账号。
- 预期：
  1. 登录成功但 `data.user.must_change_password=true`；前端应跳转强制改密页（配合 TC-I-03）。

#### TC-B-02 强制改密状态访问业务接口被拒（4031）
- 优先级：P0
- 前置：账号处于 must_change_password=1，已登录持有 token。
- 步骤：
  1. 携带该 token 调用业务接口，如 `POST /api/v1/qa/chat` 或 `GET /api/v1/documents`。
- 预期：
  1. HTTP 403 / `code="4031"`（凭证有效但功能受限，提示需先修改密码）；
  2. 与 401（未授权）语义区分；前端应跳强制改密页；
  3. 该被拒请求写入审计。

#### TC-B-03 强制改密状态可访问改密与 me
- 优先级：P0
- 步骤：
  1. 携带 must_change token 调用 `POST /api/v1/auth/change-password`（合法入参）；
  2. 携带 must_change token 调用 `GET /api/v1/auth/me`。
- 预期：
  1. 两个接口均正常放行（must_change 例外路径），返回相应成功结果。
- 备注：除 `change-password` 与 `me` 外，其余业务接口在改密完成前均被 4031 拦截。

#### TC-B-04 修改密码成功（满足强度）
- 优先级：P0
- 前置：账号处于 must_change_password=1 且已登录。
- 步骤：
  1. `POST /api/v1/auth/change-password`，body `{"old_password": "123456", "new_password": "Admin12345"}`。
- 预期：
  1. HTTP 200，`code="0"`，提示改密成功需重新登录；
  2. `zd_user.must_change_password=0`，`pwd_changed_at` 更新。

#### TC-B-05 改密后旧 token 失效需重新登录
- 优先级：P0
- 前置：已完成 TC-B-04。
- 步骤：
  1. 携带改密前签发的旧 token 调用 `GET /api/v1/auth/me` 或任一业务接口。
- 预期：
  1. 返回 HTTP 401 / `code="4010"`（pwd_changed_at 快照落后，旧 token 作废）；
  2. 用新密码重新登录成功，用旧密码登录失败。

#### TC-B-06 弱密码被拒
- 优先级：P0
- 步骤（对处于强制改密的账号分别尝试）：
  1. 新密码不足 8 位（如 `Ab1`）；
  2. 新密码纯字母（如 `abcdefgh`）；
  3. 新密码纯数字（如 `12345678`）。
- 预期：
  1. 均被拒绝，返回密码强度不满足提示（至少 8 位且同时包含字母与数字）。
- 备注：密码强度规则为 Assumption/TBD，若企业统一密码策略上线则以策略为准。

#### TC-B-07 改密完成后业务功能恢复正常
- 优先级：P0
- 前置：完成改密并重新登录。
- 步骤：
  1. 携带新 token 调用任一业务接口。
- 预期：
  1. 正常通过，不再出现 4031；`/auth/me` 返回 `must_change_password=false`。

### 4.3 模块 C：用户管理（admin）

#### TC-C-01 管理员创建业务员账号
- 优先级：P0
- 前置：admin 已完成强制改密，持有 admin token。
- 步骤：
  1. `POST /api/v1/users`，body `{"username": "sales01", "display_name": "销售一", "password": "123456", "role": "user"}`。
- 预期：
  1. HTTP 200，`code="0"`，返回新账号信息；
  2. 新账号 `must_change_password=1`（初始密码需强制改密）、`is_active=1`、role=user；
  3. 该新账号可立即登录。

#### TC-C-02 用户名重复创建被拒
- 优先级：P1
- 步骤：
  1. 再次以 `username="sales01"` 调用创建接口。
- 预期：
  1. 返回失败（业务错误码），提示用户名已存在；`zd_user` 不产生重复记录。

#### TC-C-03 管理员重置密码并清锁定
- 优先级：P0
- 前置：业务员账号存在。
- 步骤：
  1. 先制造该账号锁定（连续输错）或正常状态；
  2. `PATCH /api/v1/users/{id}`，body `{"reset_password": "NewPass123"}`。
- 预期：
  1. 返回成功；账号 `must_change_password=1`；
  2. `failed_attempts` 与 `locked_until` 被清空；
  3. 该账号旧 token 即刻失效（密码变更），需用新密码登录并走强制改密。
- 备注：设计文档 §8.2 允许 `reset_password` 与 `is_active` 同传，可一并断言。

#### TC-C-04 停用账号立即失效（含已签发登录态）
- 优先级：P0
- 前置：业务员已登录持有 token；确认该账号当前未被锁定（若已锁定，第 3 步登录会返回 4230 而非统一错误提示）。
- 步骤：
  1. `PATCH /api/v1/users/{id}`，body `{"is_active": 0}`；
  2. 携带该业务员已签发的 token 调用业务接口；
  3. 尝试用该账号密码登录。
- 预期：
  1. 步骤 2 返回 HTTP 401 / `code="4010"`（停用即时失效，含已签发登录态）；
  2. 步骤 3 登录返回统一「用户名或密码错误」。

#### TC-C-05 启用已停用账号恢复可用
- 优先级：P1
- 步骤：
  1. `PATCH /api/v1/users/{id}`，body `{"is_active": 1}`；
  2. 该账号正确密码登录。
- 预期：
  1. 登录成功，恢复正常使用。

#### TC-C-06 禁止停用最后一个启用 admin
- 优先级：P0
- 步骤：
  1. 若系统中启用态 admin 仅剩 1 个，对该 admin 执行停用。
- 预期：
  1. 请求被拒绝（业务错误），停用不生效；系统始终保有可用管理员。
- 备注：保护规则见设计文档 §8.2；测试时注意勿在真实环境误操作。

#### TC-C-07 业务员访问用户管理接口被拒
- 优先级：P0
- 前置：持有业务员 token。
- 步骤：
  1. 调用 `GET /api/v1/users`、`POST /api/v1/users`。
- 预期：
  1. 返回 HTTP 403 / `code="4030"`；被拒请求写入审计。

#### TC-C-08 用户列表分页与模糊查询
- 优先级：P1
- 步骤：
  1. 以 admin 调用 `GET /api/v1/users?page=1&page_size=10&username=sales`。
- 预期：
  1. 返回分页结构，`sales01` 被过滤命中；`username` 模糊匹配生效。

### 4.4 模块 D：API 密钥管理（admin）

#### TC-D-01 创建密钥：明文仅创建时返回一次
- 优先级：P0
- 前置：admin token。
- 步骤：
  1. `POST /api/v1/api-keys`，body `{"key_name": "信披中心", "ip_whitelist": ["127.0.0.1"], "expires_at": null}`。
- 预期：
  1. 返回成功，`data` 含明文密钥（`zd_` 开头）；
  2. 再次查询列表/详情**不含**明文；
  3. DB `zd_api_key.key_hash` 为 sha256 摘要，不存明文。
- 备注：明文只此一次，测试须当场保存，丢失需重新创建。

#### TC-D-02 密钥列表不含明文
- 优先级：P0
- 步骤：
  1. `GET /api/v1/api-keys`。
- 预期：
  1. 返回密钥名称、状态、过期时间等，不含明文密钥字段。

#### TC-D-03 密钥有效调用推送接口成功
- 优先级：P0
- 前置：密钥已创建且绑定 IP 包含本机地址。
- 步骤：
  1. 携带 `X-Api-Key: <明文>` 调用 `POST /api/v1/ai-check/projects`（有效入参）。
- 预期：
  1. 通过准入，进入业务处理并返回成功；审计记录 caller_type=key。
  2. 同法验证 `POST /api/v1/ai-check/files`。

#### TC-D-04 无效/停用/过期/IP 不符密钥统一拒绝（401）
- 优先级：P0
- 步骤（分别构造 4 种场景）：
  1. 随机伪造密钥调用推送接口；
  2. 停用某密钥后携带调用；
  3. 设置 `expires_at` 为过去时间后携带调用；
  4. 密钥 `ip_whitelist` 不含来源 IP（如绑定 `192.168.1.1`）时携带调用。
- 预期：
  1. 均返回 HTTP 401 / `code="4010"`，提示为统一「未授权」，**不区分具体原因**（防暴露密钥状态）；
  2. 被拒请求写入审计。
- 备注：「统一 401 不区分原因」对应需求 §5.4 异常处理，属 `[Assumption, TBD]`；若业务确认需区分再调整断言。

#### TC-D-05 密钥启用/停用即时生效
- 优先级：P0
- 步骤：
  1. `PATCH /api/v1/api-keys/{id}`，body `{"is_active": 0}` 后携带调用 → 401；
  2. 再 `{"is_active": 1}` 后携带调用 → 通过。
- 预期：
  1. 停用即时失效、启用即时恢复，无需重启。

#### TC-D-06 密钥轮换：新 key 生效、旧 key 立即失效
- 优先级：P0
- 前置：存在启用密钥并保存明文。
- 步骤：
  1. `POST /api/v1/api-keys/{id}/rotate`；
  2. 用旧明文调用推送接口；
  3. 用新明文调用推送接口。
- 预期：
  1. 轮换返回新明文；
  2. 旧明文请求返回 401/4010（立即失效）；
  3. 新明文请求通过。
- 备注：用于怀疑泄露时应急；旧记录删除、新记录生成（设计 §4.3）。

#### TC-D-07 业务员/非管理员访问密钥管理被拒
- 优先级：P0
- 前置：业务员 token。
- 步骤：
  1. 调用 `GET/POST/PATCH /api/v1/api-keys*` 及 rotate 接口。
- 预期：
  1. 返回 HTTP 403 / `code="4030"`。

#### TC-D-08 密钥修改（IP 白名单 / 过期时间）生效
- 优先级：P1
- 步骤：
  1. `PATCH /api/v1/api-keys/{id}` 更新 `ip_whitelist` / `expires_at`；
  2. 按新/旧规则分别携带调用。
- 预期：
  1. 新规则立即生效（如新增的 IP 可通过、移除的 IP 被拒、新过期时间到期后失效）。

### 4.6 模块 F：访问限流

> 限流用例对「次数」敏感，建议单独环境/单独时间窗口执行；所有断言在身份识别之后按分组配额执行（需求 §5.6.1）。

#### TC-F-01 问答按 IP 限流（10 次/分钟）
- 优先级：P0
- 前置：同一来源 IP（本机 127.0.0.1），携带**有效凭证**发起请求（认证在限流之外层，认证失败会短路返回、不消耗限流计数，故 IP 维度测试需用有效身份触发）。
- 步骤：
  1. 用同一业务员 token 连续调用 qa 组接口（如 `GET /api/v1/qa/chat/gethistory`）共 11 次。
- 预期：
  1. 同一 IP 维度第 11 次（超过 10/min）返回 HTTP 429 / `code="4290"`，提示稍后重试；
  2. 审计记录 status=rate_limited。
- 备注：qa 组配额来自 `RL_QA_IP_PER_MIN=10`，IP 桶先于 user 桶（30/min）命中；超限请求同样落审计。

#### TC-F-02 问答按用户限流（30 次/分钟）
- 优先级：P0
- 前置：业务员 token，限额内；**临时将 `RL_QA_IP_PER_MIN` 调大（如 100）**（否则同 IP 第 11 次起会被 IP 桶 10/min 拦截，测不到 user 维度；或改用多 IP 轮流触发）。
- 步骤：
  1. 用同一用户 token 连续调用 qa 组接口至 31 次。
- 预期：
  1. 第 31 次返回 429/4290；此前调用正常。
- 备注：user 桶配额 `RL_QA_USER_PER_MIN=30`；测试后恢复 IP 配额原值。

#### TC-F-03 问答按密钥限流（30 次/分钟）
- 优先级：P1
- 前置：有效密钥；**临时将 `RL_QA_IP_PER_MIN` 调大（如 100）**（同 TC-F-02，避免 IP 桶 10/min 先命中）。
- 步骤：
  1. 用同一密钥连续调用 qa 组接口至 31 次。
- 预期：
  1. 第 31 次返回 429/4290。
- 备注：key 桶配额 `RL_QA_KEY_PER_MIN=30`；测试后恢复 IP 配额原值。

#### TC-F-04 评测触发限流（1 次/分钟）
- 优先级：P0
- 前置：admin token。
- 步骤：
  1. 连续 2 次调用 `POST /api/v1/eval/run`（或 `eval/gen/run`）。
- 预期：
  1. 第 2 次返回 429/4290（admin 维度 1/min，防止误触发全量评测）。
- 备注：若第 1 次触发了长任务，任务不被中断（见 TC-F-06）。

#### TC-F-05 文件上传限流（5 次/分钟）
- 优先级：P1
- 前置：业务员 token。
- 步骤：
  1. 连续 6 次调用 `POST /api/v1/documents`（可传最小测试文件）。
- 预期：
  1. 第 6 次返回 429/4290（user 维度 5/min）。

#### TC-F-06 超限不影响已在进行中的任务
- 优先级：P0
- 前置：admin token。
- 步骤：
  1. 触发 `POST /api/v1/eval/run`（全量或小样本）使任务开始；
  2. 任务进行中再次触发 → 429/4290；
  3. 等待首个任务结束。
- 预期：
  1. 再次触发被 429 拦截，但进行中的评测任务正常完成、结果可查。
- 备注：对应需求 §5.6.3；评测任务跑在后台线程，HTTP 限流不中断已发起任务。

#### TC-F-07 不同分组配额相互独立
- 优先级：P1
- 步骤：
  1. 将 qa 组额度耗尽（任一副桶超限即返回 429 即可，不必分维度）；
  2. 立即调用非 qa 分组接口（如 `GET /api/v1/documents`）。
- 预期：
  1. 非 qa 分组接口不受影响（各分组独立建桶计数）。
- 备注：`GET /api/v1/documents` 在 [groups.py](file:///e:/PythonProject/PythonProject/ZhiDaAl/gateway/groups.py) 无显式规则，走 **default 兜底组**（user/key 60/min，仅 POST 才进 upload 组）；各分组桶维度独立，跨组互不消耗。

#### TC-F-08 服务重启后限流计数清零
- 优先级：P1
- 步骤：
  1. 触发某分组超限（429）；
  2. 重启服务；
  3. 同一维度再次发起请求。
- 预期：
  1. 重启后计数归零，请求恢复放行（内存实现，属已确认边界）。
- 备注：对应需求 §5.6.4；若后续接入 Redis 则该用例改为验证分布式计数。

#### TC-F-09 默认兜底配额（60 次/分钟）
- 优先级：P1
- 前置：业务员 token。
- 步骤：
  1. 连续 61 次调用任一 default 分组接口（如 `GET /api/v1/kb/stats`）。
- 预期：
  1. 第 61 次返回 429/4290（default 组 user 维度 60/min）。
- 备注：default 组按实现维度为 user/key（见 [ratelimit.py](file:///e:/PythonProject/PythonProject/ZhiDaAl/gateway/ratelimit.py)），无 IP 维度，与需求文档 §5.6 表「按 IP 60/min」存在差异，属待确认项 3 影响面，测试时以实际配额为准。

  1. 新调用在 precheck 阶段被拦截，返回 HTTP 429 / `code="4291"`，提示「当日模型用量已用尽」；
  2. 超限前的调用正常。
- 备注：限额为全模型共用总限额（chat/rewrite/embedding 合计）。**依赖：HTTP 429 / `code="4291"` 由业务层将 `QuotaExceeded` 异常映射为 4291 返回**，若业务层未映射需先确认该链路。

#### TC-H-07 限额次日自动恢复
- 优先级：P1
- 前置：当日已超限。
- 步骤：
  1. 模拟跨日（修改系统日期或直接操作 `usage._current_date`/重启并在新日期发起调用）。
- 预期：
  1. 新自然日额度恢复，调用放行；前一日累计值异步落库 `zd_model_usage`。

#### TC-H-08 进行中评测中途超限不中断（批量豁免）
- 优先级：P0
- 前置：`DAILY_TOKEN_LIMIT` 较小值；启动一次评测后台任务。
- 步骤：
  1. 评测任务进行中，其他渠道发起的模型调用已触发 4291；
  2. 等待评测任务完成；
  3. 查看用量落库。
- 预期：
  1. 评测任务（批量豁免线程）不因超限中断，持续进行至完成；
  2. 结束按实际用量落库，超限部分如实记录（供对账）；
  3. 主线程普通调用在预检处被拦（与任务内放行对比）。
- 备注：对应需求 §5.9.3；关联 `usage.set_batch()` 线程局部标记。

#### TC-H-09 单类模型故障不影响其他类
- 优先级：P1
- 前置：mock chat 模型持续失败。
- 步骤：
  1. 在 chat 失败的同时调用 embedding（向量化）或 rewrite 功能。
- 预期：
  1. 非故障类模型正常可用（chat 与 embedding 独立包装与实例）。
- 备注：对应需求 §5.8.4。

#### TC-H-10 用量看板：今日用量与限额剩余
- 优先级：P0
- 前置：admin token，当日存在用量。
- 步骤：
  1. `GET /api/v1/usage/today`。
- 预期：
  1. 返回各角色（chat/rewrite/embedding）input/output/total 及当日总用量、限额、剩余。

#### TC-H-11 用量趋势：近 90 日逐日趋势
- 优先级：P1
- 前置：库中存在多日 `zd_model_usage` 数据。
- 步骤：
  1. `GET /api/v1/usage/trend`。
- 预期：
  1. 返回近 90 日逐日 total_tokens 序列（可绘图），按 `(stat_date, model_kind)` 汇总。
- 备注：当日实时值在进程内存中，跨日后落库进入趋势（见 [usage.py](file:///e:/PythonProject/PythonProject/ZhiDaAl/llm_gateway/usage.py)）；若产品要求当日也进趋势，需评估补充快照。

#### TC-H-12 用量落库唯一键合并
- 优先级：P1
- 步骤：
  1. 同一自然日多次累计后查看 `zd_model_usage`。
- 预期：
  1. 每 `(stat_date, model_kind)` 仅一行，数值为当日累计（`ON DUPLICATE KEY UPDATE` 合并）。

### 4.9 模块 I：前端

> 以下用例为手工 UI 验证，前置：前端 dev server 启动，后端已就绪。

#### TC-I-01 登录页登录成功进入业务页
- 优先级：P0
- 步骤：
  1. 未登录访问任意业务页 → 被守卫拦截跳 `/login`；

#### TC-I-02 登录失败提示统一友好
- 优先级：P0
- 步骤：
  1. 输入错误密码提交。
- 预期：
  1. 页面提示「用户名或密码错误」统一文案，不区分账号不存在/停用/密码错误；
  2. 锁定场景提示稍后再试（4230 分支）。

#### TC-I-03 首次登录强制改密流程
- 优先级：P0
- 前置：存在 must_change_password=1 的账号。
- 步骤：
  1. 使用该账号登录；
  2. 观察页面与业务操作。

#### TC-I-04 token 持久化与自动附加
- 优先级：P0
- 步骤：
  1. 登录后刷新页面（F5）；
  2. 打开 DevTools 观察业务请求 Header。
- 预期：
  1. 刷新后仍保持登录（localStorage 持久化）；
  2. 所有业务请求（含 SSE `chatStream`）自动带 `Authorization: Bearer <token>`；
  3. 退出登录清除 token 并回登录页。

#### TC-I-05 401 统一跳登录
- 优先级：P0
- 步骤：
  1. 在 DevTools 将 token 篡改为无效值，或停用当前账号后发起请求。
- 预期：
  1. 收到 401 后自动清除 token 并跳转 `/login`，不出现死循环（守卫已登录校验兜底）。

#### TC-I-06 403/4031/429/423 分支提示
- 优先级：P0
- 步骤：
  1. 业务员访问管理页面 → 4030 → 提示无权限（页面级不可达）；

  3. 触发限流 → 4290 → 提示稍后重试；
  4. 锁定账号登录 → 4230 → 提示稍后再试。
- 预期：
  1. 各分支提示与跳转符合统一响应语义。

#### TC-I-07 路由守卫与角色可达性
- 优先级：P0
- 步骤：

  1. 未登录 → 跳 `/login`；

- 预期：
  1. admin 可见「系统管理」分组（用户管理/密钥管理/审计/用量）与评测触发、文档删除等管理员专属入口；

- 所有 P0 用例 100% 通过；P1 用例通过率 ≥ 95%（未通过项需有明确风险说明）；
